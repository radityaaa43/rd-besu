## Steps (stop at the first error; one line per step with block/time)
**T-24h** final text to the orchestrator; Lensa users told. **T-1h** checks: item 9, old nodes healthy, `ptx_queryPendingTransactions` -> `[]` on 4 old nodes, 8 validators up (n=8 rule: bi, bank-a, bank-b all up), `free -m` >= 1.5 GiB.
1. **Freeze Lensa** (once): `systemctl --user stop lensa.service`; hold the cluster lock (flock; no port-forward inside it). Quote `systemctl --user is-active lensa.service` -> inactive.
2. **Quiesce**: `ptx_queryPendingTransactions` ([{limit:20},false]) -> `[]` on all 4 old nodes (quoted).
For each party in order **bank-a (node2), bank-b (node3), bank-c (node4), bi (node1)**:
3. **Fresh copy**, old node UP: `pg_dump -Fc -U postgres postgres` (old sidecar, `-c postgres`) piped into `pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner` in `paladin-pg-0` of the new ns (bank-c: two kubeconfigs, one pipe, 2400 s timeout, memory guard, bytes quoted). Then `compare-counts.py` old vs new.
4. **Stop the old node**: `kubectl -n paladin scale sts paladin-node<N> --replicas=0` (not deleted; the old operator never touches replicas, paladin_controller.go:297-306). **Consistency check**: counts from a throwaway read-only `postgres:17.6` pod on the old PVC (`default_transaction_read_only=on`) equal the new copy except `indexed_blocks`; if they differ, re-dump from that pod and restore again (nothing was written to the old PVC beyond WAL).
5. **Open transport**: `kubectl -n rd-zeto-<p> delete netpol rehearsal-no-9000-egress` (S1 policy, selects app=paladin only).
6. **START**: `kubectl -n rd-zeto-<p> scale sts paladin-node<N> --replicas=1`; wait Ready. The operator pod spec has a 2 s liveness probe (3 failures) and no requests: watch restarts for 10 min; a restart loop (exit 137, memory note on the 2026-11-10 crash loop) = STOP and report, rollback below.
7. **Proofs** (port-forward 8548 of the new pod, outside flock): tx id list `ptx_queryTransactionsFull` (limit 60) equals the old node's saved list; `bi@node1` (known names only) resolves to `owners.BI` of `state/zeto.json` and address `0xc77e80b8878c2509552b16336d5fc9bb0dc415a9` (only after the DB restore: `ptx_resolveVerifier` is not a pure read); `keymgr_sign` -> RPC error (disabled); nc/openssl positives to the other new LBs; `openssl s_client` without a client cert is refused.

## Rollback rule (c)
Until the new node of that party **submits its first tx** (including the S11 republish tx counts as its first tx): `scale sts paladin-node<N> -n rd-zeto-<p> --replicas=0`, re-create `rehearsal-no-9000-egress` (render from the S1 sha), `scale sts paladin-node<N> -n paladin --replicas=1`, republish nothing (old endpoint untouched). After the first tx: roll forward only (the signer nonce lives in the new DB: transaction_orchestrator.go:259-279), fix on the new node. Because the S11 republish is itself a tx, the safe rollback point is steps 3-7; after step 8 starts, roll forward.

## Outage per party (estimate, measured parts)
dump+restore 65-100 s same cluster (2.4 GB logical, 165 MB dump), bank-c cross-cluster measured 47 s; start 2-5 min (unmeasured, first start of a ~12-day-old DB); proofs + republish 3-5 min; ~10-12 min per party, ~45-50 min for four, plus freeze/unfreeze and VERIFY: about 90 minutes window, Lensa down about 45 minutes.

## Risks
Paladin pods get requests/limits only from the namespace LimitRange (3Gi limit is a guess: first-start ZK proving peak unmeasured): an OOM kill at the limit is possible, then STOP and raise it. The first start may re-run migrations (autoMigrate true) on the copied DB. During the window the four nodes are cut one by one: new-to-old messaging does not work (old nodes cannot reach the new LB path and the new nodes' registry entries point to LB IPs until step 8), which is why Lensa stays frozen for the whole window. S5b (old validators) and S22 (delete old ns) are NOT part of this window.
