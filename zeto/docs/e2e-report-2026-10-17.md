- Log of the failing tx (node1): assembled with 2 states written, submitted four times, each `Base ledger transaction ... FAILED`, finalised `reverted (revertCount=4)`; same shape for run 1's tx 1bb966aa. Two input states were imported from the sequencer snapshot ("ImportSnapshot ... not found in snapshot states") before the first assembly.
- Settled with read-only queries (ptx_getTransactionFull of 4cd3b66c, pstate queryContractStates "all" on the DFABI token, node1 log), no tx sent:
  - The tx was a transfer of 9701 to investor2@node2 (as intended). Four assemblies each wrote outputs 9701 + change 1899, so the inputs summed to 9701 + 1899 = 11600.
  - Unspent unlocked states of bondCustodian at that moment: 0, 2000, 0, 2000, 1900, 1900, 1900 = 9700 (matches `balanceOf`). 11600 - 9700 = 1900, so exactly one 1900 state was counted twice.
  - The on-chain revert is `UTXODuplicate(0x2b71d2de...)` (revert data 0xdd574831 + that id). `zeto_base.sol` reverts UTXODuplicate when two sorted inputs are equal. 0x2b71d2de is a 1900 state of bondCustodian created at 17:32:29.656, 4 s before the tx, and the node1 log shows it re-imported into the domain context ("Upserting state 0x2b71d2de... (no create lock)") at the start of the first assembly.
  - So: `buildInputsForExpectedTotal` pages on `.created > lastStateTimestamp`. After the 7 real states the next page returned the same state again (the context copy of a just-created state, apparently with a later `created` than the DB copy), the total passed 9701, and the PD210033 exhaustion check never fired. The duplicate is only caught by the contract.
  - Why intermittent: it needs the previous tx's fresh output to be re-imported into the context while the next transfer is assembled (run 2 had more time between steps). The re-import timestamp is inferred from the log and the arithmetic, not read from the source.
- Verdict: real Paladin v1.0.0 gap, not a test artefact. Effect: a transfer above the unlocked balance is not refused at assemble with PD210033; it is proven and submitted, reverts on chain (revertCount 4), and leaves 4 phantom unconfirmed 9701 output states in the originator's context. No loss of funds (the contract rejects the duplicate). Not fixed here (upstream code); the test keeps asserting PD210033, so N6 stays FAIL by design.
- Same pattern can hit any transfer whose total needs the newest state and exceeds the balance. A normal transfer within the balance is unaffected.
