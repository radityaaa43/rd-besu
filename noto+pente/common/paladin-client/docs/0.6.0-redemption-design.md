## 1. `getHolders(token)`

### Verified pattern

- `client.ts:454-456` (inside `verifyDelegatedLeg`): finds the `NotoCoin` state schema via
  `sdk.pstate.listSchemas(domain)` + `s.signature.includes("NotoCoin(")`.
- `client.ts:462`: `sdk.pstate.queryContractStates(domain, tokenAddress, coinSchema.id, {}, "all")`
  -- empty filter `{}` returns every state for every owner, each
  `{id, data: {owner, amount}}` (confirmed at `client.ts:463-464,470-477`).
- `client.ts:788-794` (`balances()`): the locked-coin side of the same pattern --
  `sdk.pstate.queryContractStates("noto", tokenAddress, schemaId, {eq:[{field:"owner",value:myAddress}]}, "available")`,
  proving `NotoLockedCoin` states also carry `data.owner` directly and are queried the same
  way, just filtered by one address instead of unfiltered.
- `client.ts:809-820` (`getLockedSchemaId`): finds the `NotoLockedCoin` schema by
  `(s.definition as {name?:string}).name === NOTO_LOCKED_COIN_SCHEMA`, not by `signature`
  substring like the coin schema -- same two-schema lookup `getHolders` needs, just the two
  different matching strategies already used elsewhere in this file.
- `client.ts:1259-1267` (`health()`): `sdk.bidx.getConfirmedBlockHeight()` returns a value
  typed `number` by the SDK but confirmed live to come back as a hex string; `health()`
  already normalizes with `Number(rawHeight)`. Reuse that, not a fresh assumption.
  RPC confirmed at `/home/ecs-user/eksplorasi-paladin/paladin/sdk/typescript/src/paladin.ts:1296-1301`
  (`bidx_getConfirmedBlockHeight`).

### Correction to the suggested pattern: status must be `"available"`, not `"all"`

`StateStatus` (`/home/ecs-user/eksplorasi-paladin/paladin/sdk/typescript/src/interfaces/states.ts:69-75`)
is `"available" | "confirmed" | "unconfirmed" | "spent" | "all"`. `verifyDelegatedLeg`'s use of
`"all"` (`client.ts:462,574`) is deliberate for a *different* purpose than summing a balance:
it needs to find specific, already-known output state IDs regardless of whether they're spent
yet (the surrounding comment, `client.ts:458-461`, is about telling "not propagated to this
node" apart from "belongs to someone else", not about aggregating balances). Using `"all"` for
`getHolders` would double-count: a spent state and the unspent state(s) that replaced it would
both come back and both get summed into `owner`'s total. `balances()` -- whose whole job *is*
to sum a balance per owner -- uses `"available"` (`client.ts:788-794`), not `"all"`. `getHolders`
is doing exactly what `balances()` does, just for every owner instead of one, so it must follow
`balances()`'s status choice, not `verifyDelegatedLeg`'s.

### BI-only / notary-visibility scope

`getHolders` only sees every state truthfully when run from the token's notary's own node --
Noto's state-privacy model only distributes a coin state to its owner and the notary. Nothing
in this codebase states that assumption in a standalone comment (I looked -- there isn't one to
cite verbatim), but the codebase already gates read/write operations that depend on "this
client IS BI" via identity-equality checks on `this.verifier.lookup`, not a node check alone:
`ensureInvestorCustodianGroup`'s `isBI = this.verifier.lookup === bondCustodianLookup`
(`client.ts:1345`), and `deployAgreement`'s stricter `PD_CLIENT_WRONG_ROLE` throw at
`client.ts:1463-1464` ("only BI's own client may set itself as the Agreement's trusted bi
role"). `getHolders` should use the same `isBI`-style gate -- a client whose own `this.verifier`
is not `config.identities.bondCustodian` gets a result that is silently wrong (it only sees
its own states, not every holder's), not merely restricted, so this should be a hard client-side
refusal (`PD_CLIENT_WRONG_ROLE`), same as `deployAgreement`, rather than a quieter
`requireIdentityVerifier`-only (same-node) check.

### `owner` is a raw address, not a lookup -- deliberate, matches the spec

Unlike the rest of this client's surface (which only ever exposes lookups, e.g. the
`PD_CLIENT_INVALID_RECIPIENT` fund-safety checks on `mintToken`/`createPrivacyGroup`,
`types.ts:461,464`), `getHolders`'s `owner` is the raw Noto coin-state address, because that's
all the state carries and there is no general address-to-lookup reverse API in Paladin. The
spec itself assigns the address -> participant mapping to the backend ("map owner address ->
participant (participants.json)", spec line 58), so this is not a gap, just a boundary: paladin
returns addresses, backend resolves identities.

### Design

```ts
/**
 * Every holder of `token` as seen from THIS node, split into unlocked (`available`) and
 * locked balances, plus the block height the read was taken at. BI-only in practice: this
 * client's own identity must be `config.identities.bondCustodian` (the token's notary) --
 * throws `PD_CLIENT_WRONG_ROLE` otherwise, same gate as `deployAgreement`, because any other
 * node only sees its OWN states and would otherwise get a silently incomplete result, not an
 * empty one. `owner` is the raw coin-state address (not a lookup) -- there is no
 * address-to-lookup reverse API in Paladin; mapping address -> participant is the caller's
 * job (spec: `coupon-redemption.md`'s snapshot step).
 * `blockHeight` comes from `bidx_getConfirmedBlockHeight`, read AFTER both state queries so it
 * is never earlier than the states it describes; still a live read under a short hold, not a
 * true historical "balance at block N" (Paladin has no such API -- spec's own "Open" section).
 */
getHolders(token: string): Promise<{
  holders: { owner: string; available: string; locked: string }[];
  blockHeight: string;
}>;
```

Implementation sketch (for the lead's review, not code to merge yet): resolve the `NotoCoin`
and `NotoLockedCoin` schema ids once (reusing the exact lookups at `client.ts:454-456` and
`client.ts:809-820`), run both `queryContractStates(domain, token, schemaId, {}, "available")`
calls, fold each result into a `Map<ownerAddress, {available, locked}>` by summing
`BigInt(data.amount)` (money, not `Number()` -- same precision rule already enforced at
`client.ts:466-467`), read `getConfirmedBlockHeight()` last, convert with `Number(rawHeight)`
then back to a decimal string for the `blockHeight: string` return shape.

## 2. Acting as a configured identity other than `this.verifier`

### The actual blocker, read precisely

`prepareTradeLeg` (`client.ts:1569-1591`, declared `types.ts:621` with JSDoc at `types.ts:612-619`)
does:
```
const myAddress = await this.verifier.address();
requireLegOwner(leg.from, myAddress, legIndex, tradeId);
```
`requireLegOwner` (`client.ts:730-737`) just compares two addresses. The real constraint is
narrower than "the client can't sign as bondIssuer at all": `lockToken` (`client.ts:1051-1056`,
`token.lock(this.verifier, ...)`) and `prepareUnlock` (`client.ts:1089,1097,1101-1104`, three
separate `this.verifier`/`this.verifier.lookup` uses: `verifyLockOwner(... await
this.verifier.address() ...)`, `isLockPrepared(this.sdk, this.verifier.lookup, ...)`, and
`token.prepareUnlock(this.verifier, {lockId, from: this.verifier, ...})`) are ALL hard-coded to
`this.verifier`, the client's own connected default identity. There is no signer parameter
anywhere in this call chain today.

### The existing pattern this should extend

`requireIdentityVerifier`/`configuredIdentityLookup` (`client.ts:2241-2254`) already solve
"sign as a DIFFERENT configured identity than this client's own default", for a same-node
identity:
```ts
private configuredIdentityLookup(key: "bondIssuer" | "bondCustodian"): string {
  const lookup = this.config.identities?.[key];
  if (!lookup) throw new PaladinClientError("PD_CLIENT_MISSING_CONFIG", ...);
  return lookup;
}
private requireIdentityVerifier(key: "bondIssuer" | "bondCustodian"): PaladinVerifier {
  const lookup = this.configuredIdentityLookup(key);
  const targetNode = lookup.split("@")[1];
  if (targetNode && targetNode !== this.config.nodeId) {
    throw new PaladinClientError("PD_CLIENT_WRONG_ROLE", ...); // cross-node signing refused
  }
  return this.sdk.getVerifiers(lookup)[0];
}
```
Its doc comment (`client.ts:2224-2230`) explicitly names the dual-role case this is already
built for: "BI's own client legitimately signs as BOTH bondIssuer and bondCustodian across
different calls (e.g. issueSeries) -- they're both node1 identities on BI's own client".
Nearly every `bondCustodian`-signed write already routes through `requireIdentityVerifier`
and then signs `from: bondCustodian.lookup` directly (`recordAtom` `client.ts:1628-1631`,
`confirmSettled` `client.ts:1642-1645`, `markFailed` `client.ts:1656-1659`) -- proving Paladin
itself lets one connected client sign from ANY identity provisioned on its own node, not only
`this.verifier`. `deployAgreement` (`client.ts:1455-1464`) adds one MORE restriction on top --
`this.verifier.lookup !== bondCustodian.lookup` throws `PD_CLIENT_WRONG_ROLE` -- but that is a
deliberate business rule for that one call ("only BI's own client may set itself as the
Agreement's trusted bi role"), not a technical ceiling; it is not present on
`recordAtom`/`confirmSettled`/`markFailed`.

So the real gap for item 2 is narrow and mechanical: `lockToken`/`prepareUnlock`/
`prepareTradeLeg` need the SAME "resolve an identity key to a `PaladinVerifier`, same-node
only" substitution `requireIdentityVerifier` already does for `bondCustodian`/`bondIssuer`
elsewhere -- just threaded through these three methods, which currently don't take it.

### Options

**Option A -- `asIdentity?: "bondIssuer" | "bondCustodian"` on `prepareTradeLeg` (and
`lockToken`/`prepareUnlock` if called directly for a leg).** Resolve via
`this.requireIdentityVerifier(asIdentity ?? <default>)` to get a `PaladinVerifier`, substitute
it everywhere `this.verifier` appears in `lockToken`/`prepareUnlock`'s bodies (the signer, and
the "am I the lock owner" check), and use its `.address()` for `requireLegOwner`'s `myAddress`
instead of `this.verifier.address()`. Same-node-only, for free, by reusing
`requireIdentityVerifier` unchanged.
*Pro*: smallest diff, directly extends the one existing mechanism, keeps the restriction (same
node, only `config.identities` keys) identical to every other BI-signed call.
*Con*: every method in the `lockToken`/`prepareUnlock`/`prepareTradeLeg` chain needs the same
new optional param threaded through, so the signature change touches 3 methods, not 1.

**Option B -- a separate signing-identity override per call, e.g.
`prepareTradeLegAs(asIdentity, groupId, agreementAddress, tradeId, legIndex, recipientLookup, idempotencyKey?)`
as a new method, leaving `prepareTradeLeg` untouched.**
*Pro*: zero risk to existing callers/signature; the new coupon/redemption cash-leg call site is
the only thing that changes.
*Con*: duplicates `prepareTradeLeg`'s body (or wraps it awkwardly, since the `this.verifier`
substitution still has to reach `lockToken`/`prepareUnlock` underneath -- the duplication
doesn't actually avoid touching those two methods, it just avoids touching `prepareTradeLeg`'s
own signature).

**Option C -- a second `PaladinClient` instance, connected as `bondIssuer@node1` directly
(its own `identity` in `PaladinClientConfig`, `types.ts:134-136`), used only for the
paying-agent leg.**
*Pro*: no signature changes anywhere; `this.verifier` really IS bondIssuer for that instance,
so every existing method already works unmodified.
*Con*: a second live connection (websocket/http) per bank purely to flip identity, when
Paladin already lets one connected client sign from multiple same-node identities (proven by
`recordAtom`/`confirmSettled`/`markFailed` above) -- this ignores a capability the SDK already
has and pays a connection-management cost for nothing.

### Recommendation

Option A. It is the direct, minimal extension of a pattern this codebase already committed to
(`requireIdentityVerifier`) rather than a new mechanism (Option C) or a parallel surface
(Option B). Cost is real but contained: `lockToken`, `prepareUnlock`, `prepareTradeLeg` each
gain one new optional parameter (default preserves today's behavior exactly, so this is
backward compatible, not breaking).

```ts
/**
 * Same as today, except the signer can be a configured identity other than this client's own
 * `identity` -- same-node only (checked by `requireIdentityVerifier`, `PD_CLIENT_WRONG_ROLE`
 * otherwise), limited to `config.identities` keys. Needed for BI-paying-agent flows (coupon/
 * redemption cash leg: `bondIssuer@node1 -> holder`) where the connected client's default
 * identity may be `bondCustodian`, not `bondIssuer`. Omitting `asIdentity` keeps today's
 * behavior (signs as `this.verifier`) unchanged.
 */
prepareTradeLeg(
  groupId: string,
  agreementAddress: string,
  tradeId: string,
  legIndex: number,
  recipientLookup: string,
  idempotencyKey?: string,
  asIdentity?: "bondIssuer" | "bondCustodian"
): Promise<{ lockId: string; unlockCall: string; cancelCall: string; preparedStateId: string }>;
```

## 3. `transferCash(fromIdentity, toLookup, amount, idempotencyKey)` and `fundIssuer(amount, idempotencyKey)`

### Confirmed: the RD cash token is plain Noto, `notaryMode: "basic"`, no hooks

`spikes/primary-subscription/live-proof.ts:112`:
`.newNoto(cashIssuer, { name: "CASH", symbol: "CASH", notary: cashIssuer, notaryMode: "basic" })`.
Also `spikes/agreement-primary-0.4.0/live-proof.ts:113` and
`spikes/prepare-trade-leg-live-check/live-check.ts:43` for the same `notaryMode: "basic"`
pattern on non-bond Noto tokens. No `BondTracker`-style hooks contract, no whitelist
(`InvestorList`), no `PenteExternalCall`. `basic` mode's `allowBurn` option
(`sdk/typescript/src/domains/noto.ts:43-48`) is irrelevant here -- neither method burns.

### No existing `transfer` wrapper -- new, built like `mintToken`

`client.ts` has no `async transfer`/`transferFrom` method today (confirmed by grep across the
file). `mintToken` (`client.ts:1270-1279`, declared `types.ts:462`) is the closest existing
shape -- resolves a lookup to a `PaladinVerifier` via `requireLookup`
(`this.sdk.getVerifiers(requireLookup(to, "to"))[0]`), calls `token.mint(this.verifier, {to:
toVerifier, amount, data:"0x"}, idempotencyKey)` through `submitIdempotent`, and throws a
`PD_CLIENT_*_FAILED` code with `receipt?.failureMessage` on a failed receipt
(`client.ts:1274-1276`). `token.transfer(from, {to, amount, data}, idempotencyKey)` exists in
the SDK already (`sdk/typescript/src/domains/noto.ts:288-303`, `NotoTransferParams` at
`:102-106`) with the identical shape `mint` uses.

### Design

```ts
/**
 * Plain Noto transfer on the RD cash token (`notaryMode: "basic"`, no hooks, no whitelist) --
 * same shape as `mintToken`, not the lock/unlock machinery `prepareTradeLeg` uses, because
 * there is no Agreement/Atom on this side of a coupon or redemption cash leg. `fromIdentity`
 * resolves the same way item 2's `asIdentity` does (same-node configured identity, e.g.
 * `bondIssuer` for `bondIssuer@node1 -> holder`) -- see `prepareTradeLeg`'s `asIdentity`
 * design for the shared resolution rule. `toLookup` a lookup, never a raw address (same
 * fund-safety rule as `mintToken`'s `to` -- `PD_CLIENT_INVALID_RECIPIENT` otherwise).
 */
transferCash(
  fromIdentity: "bondIssuer" | "bondCustodian" | "cashIssuer",
  toLookup: string,
  amount: string,
  idempotencyKey?: string
): Promise<void>;

/**
 * `cashIssuer` mints RD cash to `bondIssuer` -- funds the issuer account BI pays coupons and
 * redemptions out of (maker-checker in BI backend; this method itself does not gate on
 * approval, same division of responsibility as every other Phase-3 mint/transfer: Paladin
 * client executes, backend's maker-checker decides when to call it). Plain `mintToken` shape,
 * signer is `cashIssuer` instead of `this.verifier` -- same `asIdentity`-style resolution as
 * `transferCash`.
 */
fundIssuer(amount: string, idempotencyKey?: string): Promise<void>;
```

### Connection to item 2

`fromIdentity`/`fundIssuer`'s signer both need the identical same-node identity resolution as
`asIdentity` (item 2, Option A) -- `requireIdentityVerifier` extended to also accept
`"cashIssuer"`, which means `config.identities` (`types.ts:159-164`) needs a new optional
`cashIssuer?: string` field alongside `bondIssuer`/`bondCustodian`. These three methods
(`prepareTradeLeg`'s `asIdentity`, `transferCash`'s `fromIdentity`, `fundIssuer`'s implicit
`cashIssuer` signer) should all route through the one resolver, not three separate ad hoc
lookups.

## 4. `burnBond(token, amount, idempotencyKey)` by the custodian

### Noto has no on-chain `burn` -- it's a domain-level (Go) verb, same shape as `mint`/`transfer`

`solidity/contracts/domains/noto/Noto.sol` (grepped `^    function` across the whole file):
no `burn`/`burnFrom` function anywhere in the base-ledger contract -- confirmed by the grep,
not assumed. `solidity/contracts/domains/interfaces/INotoPrivate.sol:1-35` declares
`burn(uint256 amount, bytes data)` and `burnFrom(string from, uint256 amount, bytes data)`
with the file's own doc comment (`:4-7`): "This is the ABI of the Noto private transaction
interface, which is implemented in Go. This interface is never expected to be implemented in
a smart contract." The SDK calls it exactly like `mint`/`transfer`:
`sdk/typescript/src/domains/noto.ts:325-351` -- `burn(from, {amount, data}, idempotencyKey)`
and `burnFrom(from, {from: target, amount, data}, idempotencyKey)`, both
`TransactionType.PRIVATE` sends through `notoPrivateJSON.abi`, identical shape to `mint`
(`:260-277`) and `transfer` (`:288-303`).

### `burnFrom` is hooks-mode only, and `onlySelf` still means the TX submitter, not the token holder

`domains/noto/internal/noto/handler_burn_from.go:19-23`: `Init` rejects `burnFrom` outright in
basic mode (`MsgBurnFromNotAllowed`) -- only plain `burn` works in basic mode. Both go through
`handler_burn_common.go`'s `hookInvokeBurn` (`:208-241`), which builds `BurnHookParams{Sender:
senderID.address, From: fromID.address, ...}` where `senderID` resolves `tx.Transaction.From`
(the real transaction submitter) and `fromID` resolves the `from` parameter (`burn`: always the
submitter itself; `burnFrom`: whoever's balance is being burned, which can differ from the
submitter). That `Sender`/`From` pair is exactly what reaches the Solidity hook's `sender`/
`from` parameters.

`NotoTrackerERC20.sol:131-138` (upstream default `onBurn`, confirmed BondTracker does NOT
override it -- grepped `function on` in `BondTracker.sol`: only `onMint`, `onTransfer`,
`onUnlock`, `onPrepareUnlock`, `handleDelegateUnlock` appear; no `onBurn`, no `onLock`):
```solidity
function onBurn(address sender, address from, uint256 amount, bytes calldata data, PreparedTransaction calldata prepared)
    external virtual override onlySelf(sender, from) { _onBurn(sender, from, amount, data, prepared); }
```
`onlySelf` (`NotoTrackerERC20.sol:21-24`): `require(sender == from, "Sender is not the from
address")`. Because `sender` is the real TX submitter (not derived from `from`), this means:
for `burn`, `sender == from` always holds (you can only ever burn your own balance). For
`burnFrom`, it holds ONLY when the submitter and the burned-from account happen to be the same
address -- i.e. `burnFrom` on `BondTracker` can never actually burn someone ELSE's balance; it
degenerates to the same constraint as plain `burn`. `_onBurn` (`NotoTrackerERC20.sol:61-64`)
calls OpenZeppelin `ERC20._burn(from, amount)`, which correctly decrements `ERC20.totalSupply()`
-- no bug on the private-tracker side.

**Constraint this puts on `burnBond`**: the custodian can only burn bond units it ALREADY
holds as its own balance. For redemption, that means the bond leg (holder -> custodian) MUST
settle first; only then can the custodian call plain `burn` (not `burnFrom`) on its own
resulting balance. This is exactly the ordering the spec already specifies (Flow 2 step 4:
"Returned bonds burned by custodian" after the bond leg lands), and it is not optional --
`burnFrom` cannot substitute for it on this contract.

### The real `totalSupply` finding: it's the PUBLIC tracker, and it IS in scope per the spec

Spec (`docs/superpowers/sdd/2026-10-06-coupon-redemption.md`, "Capabilities needed per layer"):
"`burnBond(token, amount, idempotencyKey)` by the custodian, and a check that BondTracker's
hooks allow the redemption transfer holder -> custodian and the burn. Fix the known
`totalSupply` not decreasing on burn if the public tracker is used for supply." -- this is
listed as a paladin capability needed for THIS task, not deferred.

Cross-checked against both trackers:
- **Private tracker** (`NotoTrackerERC20`/`BondTracker`): `totalSupply()` is OpenZeppelin
  ERC20's own counter, correctly decremented by `_burn` on every burn. No bug here.
- **Public tracker** (`BondTrackerPublic.sol`): has its OWN, separate `uint256 public
  totalSupply` (`:50`), incremented on `onIssue` (`:93`, `totalSupply += amount`), with NO
  function anywhere in the file that decrements it. `BondTracker.sol`'s `onMint` and
  `onTransfer` (and the distribution-sale branch of `onUnlock`/`handleDelegateUnlock`) each
  `emit PenteExternalCall(_publicTracker, abi.encodeWithSignature(...))` to notify the public
  side (`onMint` -> `onIssue`, sale-path `onTransfer`/`onUnlock` -> `onDistribute`) -- `onBurn`
  does NOT exist as an override on `BondTracker.sol` at all (confirmed above), so there is
  categorically no `PenteExternalCall` for a burn, and no `onBurn`-shaped function exists on
  `BondTrackerPublic.sol` for one to call even if there were. The public tracker's
  `totalSupply` genuinely never learns about a burn -- not "doesn't decrement it correctly",
  but "is never told it happened".

**Scope boundary**: fixing this requires a Solidity change on BOTH `BondTracker.sol` (add an
`onBurn` override that emits a new `PenteExternalCall`) AND `BondTrackerPublic.sol` (add the
function on the receiving end to decrement its `totalSupply`). `BondTracker.sol` and its test
file are explicitly owned by another agent right now, and this design doc does not touch
Solidity. I'm flagging this as a required contract-side follow-up for the lead to route --
either to whoever already owns `BondTracker.sol` (since the change lands in the same file as
their custodian-exemption fix), or as its own separately-scheduled task -- NOT designing the
Solidity fix here.

### Design

```ts
/**
 * Burns `amount` of `token` from the CUSTODIAN's own balance -- Noto has no on-chain `burn`
 * (it's a domain-level verb, same shape as `mint`/`transfer`: INotoPrivate.sol's doc comment,
 * "implemented in Go, never expected to be implemented in a smart contract"). `BondTracker`
 * does not override `onBurn`, so it falls through to the upstream default, gated by
 * `onlySelf(sender, from)` -- the burn's TX submitter must equal the account whose balance is
 * burned. This means `burnBond` only ever burns the custodian's OWN already-received bond
 * (e.g. after a redemption bond leg has already landed holder -> custodian), never an
 * arbitrary holder's balance directly -- call this strictly AFTER that leg settles, never
 * before. Signs as `bondCustodian` (same `requireIdentityVerifier("bondCustodian")` pattern
 * used by `recordAtom`/`confirmSettled`/`markFailed`).
 *
 * KNOWN GAP (contract-side, out of scope for this client): the PUBLIC tracker's own
 * `totalSupply` counter (`BondTrackerPublic.sol`) is never notified of a burn -- `onMint`/
 * `onTransfer` each emit a `PenteExternalCall` to the public tracker, `onBurn` does not exist
 * on `BondTracker.sol` to emit one. If `BondTrackerPublic.totalSupply` is read anywhere as the
 * bond's outstanding supply, it will overstate it after every burn until that contract-side
 * fix lands. Flagged to the lead; not fixed here (requires editing `BondTracker.sol`, owned
 * by another agent, and `BondTrackerPublic.sol`).
 */
burnBond(token: string, amount: string, idempotencyKey?: string): Promise<void>;
```

Implementation sketch: identical to `mintToken`'s shape but calling `token.burn(bondCustodian,
{amount, data: "0x"}, idempotencyKey)` (SDK: `sdk/typescript/src/domains/noto.ts:325-337`)
through `submitIdempotent`, signer resolved via `this.requireIdentityVerifier("bondCustodian")`
(`client.ts:2247-2254`), throwing `PD_CLIENT_BURN_FAILED` on a failed receipt (same
`receipt?.success` / `receipt?.failureMessage` convention as every other submit method, e.g.
`client.ts:1274-1276`).

## Open questions for the lead

1. **Item 1 restriction mechanism**: should `getHolders` use the hard `PD_CLIENT_WRONG_ROLE`
   throw (`deployAgreement`-style, `client.ts:1463-1464`) when `this.verifier.lookup !==
   config.identities.bondCustodian`, or the softer `requireIdentityVerifier` same-node-only
   check? I recommended the hard throw (a wrong caller gets a silently incomplete, not
   visibly-refused, result otherwise) -- this is a judgment call about how strict to be, not
   something resolvable by reading more source.
2. **Item 2/3 identity set**: extending `requireIdentityVerifier`'s key union from
   `"bondIssuer" | "bondCustodian"` to also include `"cashIssuer"` means adding
   `cashIssuer?: string` to `PaladinClientConfig.identities` (`types.ts:159-164`) -- a config
   shape change every deployment's config file needs updated for. Confirming this is
   acceptable (vs., e.g., `fundIssuer` resolving `cashIssuer` some other way) is a product/ops
   call, not a code question.
3. **Item 4's contract-side gap**: is `BondTrackerPublic.totalSupply` actually READ by anything
   today (backend, frontend, another contract) as the bond's outstanding supply? If nothing
   reads it, the gap is real but currently inert, and the lead may choose to defer the
