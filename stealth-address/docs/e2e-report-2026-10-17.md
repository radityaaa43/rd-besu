## Not implemented

- **RD redeem by BI.** There is no BI redeem or issuer burn. RD only has the holder's `burn` / `burnFrom` from OpenZeppelin ERC20Burnable. RD-33..35 test that, not a BI redemption flow. Not built, as instructed.
- **RD has no certificate or allowlist lock.** Unlike the bond, the plain ERC-20 `transfer` of RD is open. It moves RD without a stealth announcement, so the recipient does not get a scan hit. That is the existing design (the ERC-20 path is there for the DvP escrow funding), not tested as a negative.
- **A list of licensed memo identities.** The contract only bounds the memo length. Which sender addresses are real banks is an off-chain list (already listed as not done in the specs).
- **On-chain verification of the certificate signature in the DvP escrow** (already listed as not done in the DvP spec).

## Notes

- The DvP trades 2 to 6 share one wait of about 100 seconds for expiry, so the full run takes about 4 minutes.
- The REG-17..19 ERC-1271 cases use the `Wallet1271` mock from the forge test build (`out/ERC6538Registry.t.sol/Wallet1271.json`), so `forge build` must have run.
- The vendor ERC-1400 reverts with a short code string (`54` = transfers halted by the certificate check, `52` = insufficient balance), not a custom error; those are asserted as the string.
