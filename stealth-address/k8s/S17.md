## 3. Deployment shape

Both roles: image above, `runAsNonRoot` user 10001, `readOnlyRootFilesystem`, drop ALL caps, `seccompProfile: RuntimeDefault`, `automountServiceAccountToken: false`, requests 50m/128Mi, limit 256Mi, replicas 1, label `app: stealth-signer` (the live `besu-rpc-ingress` policy already admits `app in (st-gw, stealth-signer)` on 8545, READ), SA `stealth-signer` (the S7 Vault policy name; unused by pods while keys come from Secrets).
Env (names from `signer/src/main.ts`): `PARTY, ROLE, PORT, CHAIN_ID, RD, BOND, ANNOUNCER, VALIDATOR, DVP_FACTORY, FROM_BLOCK, RPC_URL=http://besu-rpc:8545` (READ: Service port `json-rpc` 8545), `KEYS_DIR=/keys`, `RPC_JWT_FILE`, bank: `CERT_URL` + `TLS_DIR=/tls`; custodian: `TLS_DIR=/tls` + `BANK_SIGNERS=CN=stealth-signer-bank-a,CN=stealth-signer-bank-b,CN=stealth-signer-bank-c`. Chain constants come from `deployed.json` at window time and are quoted in the log; no value is guessed here.
Probes: `GET /health` (no key, no chain call) for startup, liveness and readiness. Readiness therefore does NOT prove the RPC node answers; the RPC proof is control C4.
Rollout: custodian first (banks depend on it only when a cert is asked), then the three banks in parallel, fail-stop per layer, a deviation = stop, report, wait, no delete.

## 4. Gateway and routes

- `st-gw-<N>`: rendered from the zeto gateway (`zeto/k8s/gateway/render.sh`) with the ns and Service changed; Lensa's client cert is the CSR flow signed by that party's CA (CN=lensa, clientAuth), same as zeto.
- Rego package `bank.stealth`: allow `POST /intent`, `GET /holdings`, `GET /history`, `GET /health` from CN=lensa; DENY `/cert` on every `st-gw` (a Lensa client never asks for certificates). Read door: existing `bi.besu` method allowlist unchanged.
- `/cert` does NOT go through Envoy. The S8 verdict rule (a) says the mTLS client cert itself must be a registered bank signer; the signer reads it from its own TLS socket. If Envoy terminated TLS, that identity would be lost. So `stealth-custodian-ext` (LoadBalancer :9443, ACL, `externalTrafficPolicy: Cluster`, ACL annotations in the first apply) points straight at the custodian pod and the pod terminates mTLS itself. OPA is not in this path; the four cert rules (a-d) in the signer are the control. This deviates from PLAN S17 text ("route for `/cert`" in the gateway): see Q2.
- LB ACL: reuse the zeto ids already in place (cluster 1 `acl-d9ji5nwbqutwulof33ydb`; bank-c source `8.215.62.92/32`, bank-a/-b same-cluster via kube-proxy). Read back first; any ACL entry change is user-only.
- NetworkPolicy: custodian pod ingress only on 9443 (from the LB health source `100.64.0.0/10` and the external CIDRs); bank signer ingress only from `app=st-gw` in the same ns on its port; `allow-same-namespace` already excludes `besu-rpc` and `vault` (READ) and must also exclude `app=stealth-signer` (opt-in, same edit as zeto did for `paladin`), otherwise any pod in the ns reaches the signer.

## 7. Open questions for lead (defaults taken in this text)

- **Q1 key path.** The Vault from S7 has injector and csi off and the signer reads files (`KEYS_DIR`), so keys reach the pod through Kubernetes Secrets in this text, as lead said. Side effect: the Vault store holds only the custody/backup copy, and `party-admin` (create pods in the ns) can mount a Secret and read it. It is the party's own key and own operator, but the S7 RED "denied from a pod in the same ns" then does not hold for a pod the operator creates. Default: Secrets, limit recorded. Alternative: a Vault agent sidecar rendering files into a tmpfs `emptyDir` (no signer change, one more image).
- **Q2 `/cert` path.** Default above (pod terminates mTLS, no Envoy). Alternative: Envoy forwards the verified client CN in a header and the signer trusts the gateway: needs a signer code change and weakens the S8 rule (a). Analyst wording may need a one-line note either way.
- **Q3 `certKey` source and RPC token.** (i) `certKey` = the custodian key of S12; until S12 runs, the only cert signer on chain is the old `deployerKey`, so the Secret would hold a COPY of it. Which one at S17 time? (ii) **Code gap found:** the signer takes `RPC_JWT_FILE`, a static token, but tokens are capped at 1 h by project rule (`mint-token.sh`) and the Secret holds the RS256 key pair, not a token. A long-lived pod needs the signer to mint per request from the key file (`node:crypto`, the "long-lived minter is signer code (S9)" line in `k8s/rpc/README.md`). I propose a small signer PR (RED test: token minted from a fixture key, `exp` <= now+900, permissions `eth|net|web3` only) BEFORE the window. Without it the signer stops answering after the first token expires.
