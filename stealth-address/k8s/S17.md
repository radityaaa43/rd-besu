## 3. Deployment shape

Both roles: image above, `runAsNonRoot` user 10001, `readOnlyRootFilesystem`, drop ALL caps, `seccompProfile: RuntimeDefault`, `automountServiceAccountToken: false`, requests 50m/128Mi, limit 256Mi, replicas 1, label `app: stealth-signer` (the live `besu-rpc-ingress` policy already admits `app in (st-gw, stealth-signer)` on 8545, READ), SA `stealth-signer` (the S7 Vault policy name; unused by pods while keys come from Secrets).
Env (names from `signer/src/main.ts`): `PARTY, ROLE, PORT, CHAIN_ID, RD, BOND, ANNOUNCER, VALIDATOR, DVP_FACTORY, FROM_BLOCK, RPC_URL=http://besu-rpc:8545` (READ: Service port `json-rpc` 8545), `KEYS_DIR=/keys`, `RPC_JWT_KEY_FILE` (file `private.pem` of Secret `stealth-rpc-jwt`; the signer mints the token, rd-besu #53), bank: `CERT_URL` + `CERT_SERVERNAME=custodian-1` (rd-besu this PR: `src/mtls.ts` `servername`) + `TLS_DIR=/tls`; custodian: `TLS_DIR=/tls` + `BANK_SIGNERS=CN=stealth-signer-bank-a,CN=stealth-signer-bank-b,CN=stealth-signer-bank-c`. Chain constants come from `deployed.json` at window time and are quoted in the log; no value is guessed here.
Probes: `GET /health` (no key, no chain call) for startup, liveness and readiness. Readiness therefore does NOT prove the RPC node answers; the RPC proof is control C4.
Rollout: custodian first (banks depend on it only when a cert is asked), then the three banks in parallel, fail-stop per layer, a deviation = stop, report, wait, no delete.

## 4. Gateway and routes

- `st-gw-<N>`: rendered from the zeto gateway (`zeto/k8s/gateway/render.sh`) with the ns and Service changed; Lensa's client cert is the CSR flow signed by that party's CA (CN=lensa, clientAuth), same as zeto.
- Rego target `stealth` (see section 4): allow `POST /intent`, `GET /holdings`, `GET /history`, `GET /health` from CN=lensa; DENY `/cert` on every `st-gw` (a Lensa client never asks for certificates). Read door: existing `bi.besu` method allowlist unchanged.
- `/cert` is TLS PASSTHROUGH on `st-gw-1` (lead 2026-11-12, replaces the own-LB default). The S8 verdict rule (a) needs the mTLS client cert on the signer's own `node:https` socket, so Envoy must not terminate it. Envoy shape (listener filter chain by SNI next to the HTTPS chain): listener `besu`-style port gets `listener_filters: [envoy.filters.listener.tls_inspector]`; the existing TLS-terminating chain (from `opa/mtls/envoy-mtls.sh`) stays the default chain; one added chain with `filter_chain_match: {server_names: ["custodian-1"]}` and `envoy.filters.network.tcp_proxy` to a `strict_dns` cluster `stealth-custodian.rd-stealth-bi:9443`, no `transport_socket`. Envoy picks the server_names chain before the default one. Feasible in the current render: `envoy-mtls.sh` today matches `^    - filters:$` and expects exactly 2 chains, so the render PR extends that script (or adds a chain after it) with an offline test and runs `envoy --mode validate` in CI (not executed here: no Envoy locally). Source: Envoy docs, "FilterChainMatch" and "TLS Inspector" listener filter. OPA is not in this path; the four cert rules (a-d) in the signer are the control; the HTTP route on `st-gw` denies `/cert`. Bank signers use SNI `custodian-1` (`servername` option in `src/mtls.ts`, to be checked in the render PR).
- **Reach (READ 2026-11-12) and decision R1 (orchestrator via lead, 2026-11-12):** all 25 cluster-1 nodes have only private IPs (172.24.x), BI's public addresses are CLBs only, so bank-c (cluster 2) cannot reach `st-gw-1` by NodePort. R1: ONE new CLB Service `st-gw-1-ext` for `st-gw-1` (same class/spec as the CLBs already approved), EXISTING ACL ids only (cluster 1 `acl-d9ji5nwbqutwulof33ydb`, source `8.215.62.92/32`; no new ACL, no new entry), ACL annotations in the FIRST apply, `externalTrafficPolicy: Cluster`, no `loadbalancer-id` (R2, a second Service on the shared CLB 8.215.50.4, is rejected). Falls under the standing GO; the extra CLB cost is noted to the user. Order inside the window: apply (rendered by `gateway/render.sh bi --acl-id ... --external-cidr ...`) -> read back the ACL on the listener BEFORE any 100.64 element (none is rendered: the gateway policy admits any source on 8550, mTLS is the gate) -> controls before traffic: positive from bank-c (C10), negative from a hosted runner (`lb-external-probe.yml`, must be refused by the ACL). Quote the LB address after creation; it becomes bank-c's `CERT_URL` (`https://<LB IP>:8550/cert`) with `CERT_SERVERNAME=custodian-1`; bank-a/-b use `https://st-gw-1.rd-stealth-bi.svc.cluster.local:8550/cert` with the same servername.
- Rendered by `stealth-address/k8s/gateway/render.sh <party> --opa-config <party opa-config.yaml>` (offline test `gateway/test.sh`; CI runs `envoy --mode validate` on all four configs and `opa test` on the rego): ConfigMaps `st-gw-<N>-envoy` and `st-gw-opa`, Deployment `st-gw-<N>` (envoy + OPA sidecar, hardened, no SA token, Secret `st-gw-<N>-mtls` optional, created by the party from the per-party CA CSR flow), Service `st-gw-<N>`, NetworkPolicies `st-gw-ingress`, `stealth-signer-ingress`; bi: passthrough chain, `stealth-custodian`, `stealth-custodian-ingress`; R1: `st-gw-1-ext`. `render.sh bundle-access <party>` renders NetworkPolicy `bundle-server-from-stealth` in `rd-zeto-<party>` (the one object outside the stealth ns: st-gw -> bundle-server :8080 only, never the 8081 sink; additive to zeto's `bundle-server-ingress`).
- OPA of `st-gw`: pulls `bi/latest.tar.gz` and `bank/latest.tar.gz` from `bundle-server.rd-zeto-<party>` (signing key id = the party, same as the zeto gateways); the config is the party's `opa-config.yaml` (with the public keys) rewritten by the render: no sink service, no bearer token, no status/decision-log service (decisions go to the console), because the stealth ns holds no sink token. Rego `bi.platform.stealth` + `bank.platform.stealth` (target `stealth`): Lensa certs only, `POST /intent`, `GET /holdings`, `GET /history`, `GET /health`, exact paths, no query string; `/cert` is never allowed. The rego only reaches the gateways in a NEW signed bundle: the zeto G4 upload path (`/sink/bundles/bi|bank`, relay) must publish the main-checkout rego BEFORE the controls, otherwise the target has no package and every request is denied (fail closed).
- **Besu read door NOT rendered (FINDING):** the S4 RPC node requires an RS256 JWT, and a gateway cannot mint one (Envoy has no RSA signer; a static token in the config expires within 1 h; Lensa holds no key). Reads Lensa needs go through the signer (`/holdings`, `/history`, `/health`). A door to the node itself needs either a signer-side `/rpc` forwarder (new code, uses the new minter) or a node without JWT behind a policy; the PLAN S17 line "read door of the RPC node" is therefore a deviation note for the analyst until lead picks one.
- **S1 re-apply (its own window line, field change on approved objects, not applied here):** `allow-same-namespace` in `rd-stealth-bi`, `-bank-a`, `-bank-b`, `-bank-c` gets the extra expression `{key: app, operator: NotIn, values: [stealth-signer]}` (rendered by `stealth-address/k8s/render.sh`; the old selector key `app.kubernetes.io/name` did not match the signer label). Do it BEFORE the signer pods exist; read back with `kubectl -n <ns> get netpol allow-same-namespace -o yaml`.
- NetworkPolicy: custodian pod ingress only on 9443 from `app=st-gw` in `rd-stealth-bi`; bank signer ingress only from `app=st-gw` in the same ns on its port; `allow-same-namespace` already excludes `besu-rpc` and `vault` (READ) and must also exclude `app=stealth-signer` (opt-in, same edit as zeto did for `paladin`), otherwise any pod in the ns reaches the signer.

## 7. Decisions (lead 2026-11-12) and the one open row

- **Q1 key path:** Kubernetes Secrets accepted. Recorded limit: `party-admin` can create pods in its ns and mount any Secret, so the S7 RED "denied from a pod in the same ns" does not cover an operator-created pod; it is the party's own key and own operator. Vault agent sidecar into tmpfs = a later hardening row for the analyst, not in this step.
- **Q2 `/cert` path:** TLS passthrough on `st-gw-1` (section 4). Deviation note vs PLAN S17 wording ("route for `/cert`" in the gateway, LB on the custodian's gateway Service): `/cert` is a passthrough chain, not an OPA-checked HTTP route, and no LB is created by this text. For the analyst's final evaluation. bank-c reach: R1 (section 4).
- **Q3a `certKey`:** the S12 custodian key only; S17 waits for S12.
- **Q3b RPC token:** signer PR mints the RPC JWT per request from the key file (RED test, `exp` <= now+900, permissions `eth|net|web3` only, key never logged); rd-besu #53, merged before the window. The signer pod therefore mounts the node's RS256 `private.pem` (by design: it is the long-lived minter).
